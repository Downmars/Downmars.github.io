# 个人博客写作指南

这份指南用于整理 Downmars 的博客，包括技术折腾、日常记录、出行计划和个人想法。给写作者看的解释和例子放在这里，给协作 agent 的执行约定放在根目录的 [AGENTS.md](../AGENTS.md)。它是仓库里的写作参考，不作为博客文章发布。

## 让读者看见这是谁的事情

“活人感”来自具体的处境和判断。为什么想做这件事，手里有什么条件，哪一步不顺，最后为什么这样选，这些内容比通用的开场白更能留下个人特点。

比如搭服务器，值得记的是已有服务占用了什么端口、为什么保留当前的反向代理、哪处配置真正解决了问题。去海边，值得记的是想拍什么、为什么住一晚、第二天早起之后还想留时间补觉。读者能看到事情怎么发生，也能看懂选择的理由。

个人博客可以短，可以偏心，也可以暂时没有答案。一篇文章只解释清楚一个决定，就已经有写下来的价值。无需把每个话题补成一套完整知识体系。

自然也需要编辑：明显的错字要改，长句要理顺，重复的话要删。原稿里的一句吐槽可以保留，但没有必要额外添加几句玩笑或感叹。口语、括号和省略号都只是表达方式，不能替代内容。

## 先选材料，再考虑怎么写

动笔前先明确这篇文章想留下什么。这个判断用于取舍，不一定要变成正文里的“本文目标”。

| 材料 | 怎么处理 |
| --- | --- |
| 作者的需求、条件和选择 | 优先保留，说明事情为什么这样发展 |
| 改变了决定的细节 | 保留，例如时间不够、已有设备可用、某个端口被占用 |
| 确实发生的失败和结果 | 保留与结论有关的部分，不把所有试错过程逐条搬进来 |
| 读者复现需要的命令、版本和路径 | 写准确；个人路径按需要换成明确的示例占位符 |
| 原稿里重复的提醒、备选项和问答 | 合并或删除，留下最后采用的方案及必要理由 |
| 网上查到的背景资料 | 只补理解本文需要的部分，标明出处 |
| 与主题关系不大的知识和建议 | 舍去；确实值得展开时另写一篇 |
| 无法确认的体验、数字和结论 | 不补写；重要的先核对，不重要的省略 |

整理多个版本时，先看作者最新的明确修改，再以指定的最终稿为底稿。不要因为旧表更详细，就把已经更换的住宿、弃用的软件或取消的安排补回来。

“完整保留原文”和“选取适合博客的部分”是两种不同任务。后者需要做编辑取舍，允许删掉材料中正确但与文章无关的内容。

## 第一人称要有依据

可以把作者提供的经历整理成“我”，但不能替作者经历事情。

| 已知材料 | 可以写 | 不应写 |
| --- | --- | --- |
| 已做出行规划，尚未出发 | “打算第二天早点去海边。” | “清晨的海风比想象中冷。” |
| 有一次成功运行的输出 | “这次在我的环境里跑通了。” | “长期使用完全稳定。” |
| 资料介绍某个功能，作者未验证 | “文档提供了这个功能。” | “我试下来确实很好用。” |
| 作者明确觉得配置麻烦 | 保留麻烦在哪里，以及自己的取舍 | 添加没有说过的愤怒、失望或兴奋 |

“折腾了一晚上”“踩了很多坑”“终于搞定了”都包含事实，不能当作润色用的连接词。作者说过、记录里有，才写。

个人偏好也要保留范围。“我的场景用不上”很清楚，不必扩大成“这个东西没有价值”。如果原稿本身有强烈评价，可以保留立场，同时把支持评价的事实和个人感受说开。

外部资料若与原稿中的可核实事实冲突，先核对。不能因为要忠于作者就保留明显错误，也不能用搜索到的一般建议覆盖作者已经做出的个人选择。

## 把泛泛的话落到具体事情上

下面是表达示例。改写只能在已有材料支持的范围内使用，不能把示例当成作者的新经历。

| 泛泛或模板化的写法 | 有材料支持时，可以这样写 |
| --- | --- |
| “通过合理规划，有效提升出行体验。” | “第一天下午先去认路，第二天摸黑出门就不用再找入口。” |
| “综合考虑后，选择了更适合自己的方案。” | “80和443端口已经给了Nginx，新服务也交给它做反向代理。” |
| “这是一款功能强大、值得推荐的工具。” | “我需要的是把几个来源放在一起看，它刚好能做这件事。” |
| “仍有诸多值得进一步探索的方向。” | “自动备份还没配，暂时只能手动做。” |

一句话如果换掉软件名、地名之后，还能原封不动放进任何文章里，就值得检查它有没有实际信息。通常有三种处理办法：补清原因，缩小范围，直接删掉。

“全面”“深度”“高效”“最佳”“极致”不是绝对禁词，但都需要内容支撑。少写形容词，给出一个具体行为或结果，往往就够了。

不用反复对读者说“首先需要明确”“值得注意的是”“接下来我们将”。上下文能接上，就直接讲下一件事。也不要每段都制造一句加粗的结论，把本来连贯的叙述切成口号。

## 按内容安排结构

开头尽早交代写这篇文章的缘由。可以从一个问题、一件小事或已经做出的决定开始，不必先讲行业趋势或概念定义。

正文里，原因和动作尽量放在一起。写完“换了一个工具”，接着解释什么问题促成了更换；给出命令，说明它解决哪一步。读者不该翻到很后面才知道前面那段为什么出现。

小标题帮助读者找内容。能写“80和443已经被占用了”，就不一定要写“环境约束与方案选择”。不过技术术语本身准确且必要时，直接使用，不要为了口语化把意思说模糊。

表格适合行程、参数和并列方案；有先后依赖的操作适合编号；解释理由和记录想法通常用段落。不要把每句话都拆成列表，也不要为了显得像随笔而藏起读者真正要找的步骤。

结尾停在当前进展、尚未解决的问题或最后一件实际事情上即可。内容讲完就结束，不必再复述全篇、劝读者行动，或把一次小折腾上升成人生感悟。

## 不同文章需要留下什么

### 技术记录

让以后遇到同样问题的自己能看懂，也让环境相近的人有机会复现。通常需要交代触发问题的场景、相关环境、实际采用的方案，以及怎么知道它有效。篇幅根据问题大小决定。

关键命令和配置不能在“去掉AI感”时一起删掉。保留必要的执行顺序、文件位置和结果；长配置可以使用仓库已有的折叠 shortcode。明显的占位符要说明替换方法，不放真实密码或令牌。

环境中已经验证的结果，与根据文档整理的步骤要分开。不要把一次启动成功写成长期稳定，也不要把为写文章临时跑通的环境说成作者一直在用的配置。

遇到可能丢数据、改变服务状态或暴露端口的操作，在相应步骤旁说明具体影响与必要前提。其他地方不重复附加通用警告。

### 出行计划与游记

计划保留日期、主要地点、交通衔接、想做的事和影响安排的条件。按实际需要放一两张时间表，其他部分解释为什么这样安排。无需补齐当地所有景点、餐馆和装备推荐。

游记则要有实际发生的事情。时间表变了什么、哪个画面拍到了、哪里和预想不同，都比通用攻略有价值。尚未出发的计划不添加现场气味、天气感受和偶遇；回来后也不为了方便，直接把所有“打算”改成“已经”。

潮汐、路况、天气和开放状态等会直接影响行动的信息，要写清适用范围。提醒集中在相关位置，内容够用即可，不让安全说明盖过整个旅行记录。

### 工具、设备和消费选择

从自己的使用场景写起，保留真正纠结的地方：已有的东西能否继续用，新方案解决什么，付出的代价是什么。最后可以选择不买，也可以仍然没有决定。

不用为每个方案平均分配篇幅，也不用凑“优缺点各三条”。对自己没有影响的参数可以不写，没用过的产品不写体验结论。

### 随笔与阶段记录

允许留下未完成的事情、前后矛盾的想法和当时的情绪。编辑时让读者能跟上意思，不急着替作者解释成一套成熟观点。

短短几段也可以成文。只有原稿确实围绕几个不同话题展开时，才分节；不用给每次碎碎念都补一段背景和总结。

### Thoughts 短记

thoughts 尽量写得短一些，几十到一两百字最好，记下一件事、一个想法或一个变化就够了。这是篇幅偏好，不必机械卡字数，也不用为了接近上限补话。

如果内容较长，涉及的东西较多，或者需要放详细步骤、配置和论证，就把这些展开成一篇正式博客。thoughts 中留一小段能独立读懂的引子或简述，说清这次发生了什么、为什么值得记，再自然地链接到详细正文。短记里不重复全文，也不要只剩一句“详情点击这里”。

详细正文按当前站点结构放在 `content/zh/posts/`，thoughts 链接到文章的实际页面；根目录 `docs/` 存放仓库说明，不作为公开博客正文的链接目标。发布时确认目标文章已生成、链接可用。

## 引用与时效

链接放在它支持的内容附近，名称让读者知道点开是什么。引用用于说明来源，不靠数量显得可靠。个人感受无需附证据，外部事实、转述观点和参考方案则要能找到出处。

易变的信息需要日期或版本语境。已经有明确日期的历史记录不必假装代表现在；面向当前使用的操作指南则应核对现状。查不到就缩小断言或省略，不写一个看似精确的数字填空。

工具输出中的引用编号、聊天内部标记、搜索追踪参数和本机私人文件路径，都不是正式引用。发布时整理成正常的链接，确认指向实际支持论述的页面。

## 可以直接给 agent 的指令

按任务选用，附上原稿路径或材料即可。它们说明编辑边界，不要求文章采用相同结构。

**从笔记整理文章：**

> 以这份材料和我最新的修改为准，挑出适合写进个人博客的部分，整理成 Markdown。保留我为什么这样选、实际做了什么和结果，删掉重复提醒、无关知识与对话痕迹。用自然的中文串起来，不补造经历、情绪或实测结果。无需把内容扩展成完整教程，完成后保存到仓库合适位置。

**润色已有文章：**

> 只做编辑：改错字、理顺句子、合并重复段落，必要时调整顺序。保留我的意思、判断和有用细节，不额外扩写背景，不把吐槽改成宣传语。遇到影响结论的事实问题先核对，别悄悄替我改变立场。

**压缩说明书味道：**

> 通读这篇文章，删掉没有信息量的套话、重复总结、机械过渡和不必要的清单。把动作与原因放在一起，保留读者实际需要的步骤、数字和限制。不靠添加口语词或故意写得凌乱来制造自然感。

**整理技术记录：**

> 根据原始记录说明问题、环境、最终采用的方案和验证结果。保留可复现的命令与关键配置，省略不影响理解的试错。区分实际运行过的内容和仅参考文档的内容，不把单次成功扩大为通用保证。

如果需要提交或推送，再在本次任务中明确要求。写作指令本身不需要夹带Git操作细节。

## 写完后，作为作者再读一遍

检查这些问题即可，不必把检查表附到每篇文章后面：

- 读者能否看懂这件事为什么发生在我身上，以及我为什么这样选？
- 文中的经历、情绪、时间和结论，原始材料里是否真的有依据？
- 是否把计划、转述或推测写成了已经发生的事实？
- 哪些段落删掉之后，文章并不会少一点有用信息？
- 必要的步骤和细节是否还在，引用是否真能支持相邻内容？
- 这些句子是否像自己会说的话，有没有突然冒出来的助手口吻或宣传语？
- 事情已经讲完的地方，是否又多写了一段空泛的结尾？
